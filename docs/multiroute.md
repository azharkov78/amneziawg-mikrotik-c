# Несколько маршрутов в одном контейнере

Опциональный supervisor запускает отдельный процесс штатного AWG-прокси на каждый
маршрут. Это выделенная из multi1/multi2 надстройка: несколько портов, серверов и
AWG-профилей в одном контейнере. Она не меняет преобразование пакетов и не требует
multi-client normal из PR #80. Один normal-процесс по-прежнему обслуживает одного
нативного WG-клиента; каждому клиенту или альтернативному пути выделяется свой порт.
Штатный server может обслуживать несколько клиентов к одному WG endpoint.

```text
WG роутера → контейнер:51821 → AWG VPS A → WG в ЦОД
           → контейнер:51822 → AWG VPS B → WG в ЦОД
```

На VPS можно использовать native AWG либо штатный server-прокси с AWG_REMOTE,
указывающим на WG в ЦОД. На обоих концах нужен согласованный AWG-профиль.
Приватные WG-ключи остаются на конечных WG-узлах. Supervisor не завершает туннель.

## Файлы

В примонтированном каталоге `/config` находятся необязательный `common.env` и
файлы маршрутов `pl.env`, `msk.env`. Примеры: `examples/multiroute/`.
Замените демонстрационные адреса, публичные ключи и H/S/J на свои.

- `common.env` задаёт общие параметры; файл маршрута переопределяет их.
- `AWG_CONFIG_DIR=/config` или `--config-dir /config` включает файловый режим;
  аргумент командной строки имеет приоритет.
- Другие унаследованные `AWG_*` в файловом режиме очищаются: Envlist контейнера
  не переопределяет настройки файлов. Служебный `AWG_PROXY_BIN` задаёт путь движка
  (по умолчанию `/awg-proxy`), а `AWG_ROUTE_NAME` выставляется supervisor.
- Формат: `AWG_NAME=value`. Внешние одинарные/двойные кавычки удаляются. Значения
  буквальные: нет shell, `$VAR`, `export`, escape-последовательностей и комментариев
  после значения. Комментарии начинаются с `#` на отдельной строке.
- Повтор ключа внутри файла — ошибка. Файлы читаются при старте; после изменения
  нужен перезапуск. Для отключения маршрута переименуйте `.env` в `.disabled`.
- В normal/reverse требуется `AWG_CLIENT_PUB`; списки ключей здесь поддерживаются
  штатным режимом server. `AWG_REMOTE` сохраняет поддержку списков/диапазонов портов.
- Разным маршрутам задавайте разные AWG_LISTEN. Для AWG_STATE_FILE используйте
  разные пути. Все процессы делят `/etc/resolv.conf`: AWG_DNS должен совпадать
  либо DNS нужно настроить извне. Относительные пути считаются от рабочего каталога
  процесса, не от каталога конфигурации; используйте абсолютные пути.

`--check` проверяет структуру файлов, обязательные поля и буквально совпадающие
AWG_LISTEN. Он не проверяет ключи, DNS, свободные порты, доступность сервера или все
значения настроек движка. Wildcard и разные записи одного адреса могут конфликтовать
при bind. Лимит 64 маршрута — ограничение парсера, не рекомендация для роутера.

## Сборка и запуск

Дополнительный Dockerfile не заменяет штатный образ и workflow релизов:

```sh
docker build -f Dockerfile.multiroute -t awg-proxy:supervisor-dev .
docker run --rm -e AWG_CONFIG_DIR=/config \
  -v "$PWD/examples/multiroute:/config:ro" awg-proxy:supervisor-dev --check
docker run -d --name awg-multi --restart unless-stopped \
  -e AWG_CONFIG_DIR=/config -v "$PWD/examples/multiroute:/config:ro" \
  -p 51821:51821/udp -p 51822:51822/udp awg-proxy:supervisor-dev
```

Для Linux без Docker: `make build build-supervisor`; затем
`AWG_PROXY_BIN=/absolute/path/awg-proxy /absolute/path/awg-supervisor --config-dir /config`.
Без AWG_CONFIG_DIR/--config-dir supervisor делает exec штатного прокси со старыми
переменными окружения: дополнительного процесса не остаётся.

Кросс-сборка статических musl-бинарников через Zig 0.14.1:

```sh
python3 tools/build-multiroute.py --arch armv7
python3 tools/build-multiroute.py --arch arm64
python3 tools/build-multiroute.py --arch amd64
```

`--image` дополнительно собирает scratch-образ через Dockerfile.multiroute-prebuilt.
ARMv7 предназначен для ac², ARM64 — ax²/ax³ и Linux ARM64, AMD64 — x86-64 Linux.
Архив контейнера для RouterOS нужно экспортировать в поддерживаемом вашей версией
формате; этот PR не публикует новые релизы или registry-теги.

## MikroTik и ресурсы

Примонтируйте каталог конфигов как `/config` и добавьте в Envlist контейнера
`AWG_CONFIG_DIR=/config`. IP контейнера один, endpoint-port WG peer выбирает маршрут.
Netwatch может менять endpoint-port, но supervisor сам не проверяет доступность
туннелей и не переключает их. Нужны независимые WAN-маршруты до VPS.

У каждого маршрута свои потоки, сокеты и буферы. Один контейнер упрощает управление,
но память растёт с количеством процессов. На ac² начинайте с малого числа маршрутов
и измеряйте память, CPU и задержки под нагрузкой. Профили AWG разных версий могут
работать в разных процессах одновременно; это не суммирование скорости путей.

При выходе дочернего процесса перезапускается только он: задержки 1, 2, 4, 8, 16,
30 секунд, сброс после 30 секунд работы. Это контроль процесса, не работоспособности
туннеля. SIGTERM/SIGINT останавливает все процессы; через пять секунд оставшиеся
получают SIGKILL и собираются waitpid. Таймаут остановки контейнера должен быть
больше пяти секунд. Логи движка помечены именем маршрута.

## Локальные проверки

`make test test-supervisor test-multiroute-transport`: штатные C-тесты, изоляция
настроек, приоритет --config-dir, старый exec-запуск, перезапуск одного маршрута,
остановка зависшего процесса, буквальные значения конфигов и обмен 200 WG-подобными
датаграммами через два независимых normal/reverse-маршрута. Это не проверка Noise,
нагрузки на физическом роутере или cookie challenge. Тесты в CI не добавляются.

ARMv5: сам supervisor собирается для ARMv5, но Zig-сборщик движка здесь поддерживает
только ARMv7/ARM64/AMD64: Clang для ARMv5 останавливается на атомиках штатного proxy.c.
Для полной ARMv5-сборки используйте GCC/musl в ARMv5-окружении с
`make build build-supervisor CC=musl-gcc`. Полный ARMv5-контейнер здесь не проверен.
